# 系统化调试

## 适用场景

任何非明显错误（不是"拼写错了改过来"那种），特别是：
- 服务器静默启动失败（无错误输出）
- 组件在画布上不显示
- 新功能加了但完全没效果
- 开发环境能跑但部署环境不行

## 4 阶段流程

### 第一阶段：现象还原

**先确认：你看到的现象是真的吗？**

1. 获取完整错误信息（不只是你目光扫到的前几行）
2. 找到错误发生的确切位置（文件、行号、调用栈）
3. 确认复现条件（什么输入触发？随机还是确定？）
4. 检查简化测试（去掉无关条件后还能复现吗？）

```
观察到的现象
  ↓
完整错误信息（全量日志）
  ↓
错误位置（文件:行号）
  ↓
复现条件（确定触发参数）
  ↓
简化测试（最小复现）
```

**产出：** `[正确理解的] 错误 = 在 [X] 条件下执行 [Y] 操作时，[Z] 组件出现了 [现象]`

### 第二阶段：根因定位

**不要直接跳到"修复"——根因和现象通常隔着几层。**

1. 沿着调用链回追：这个错误是谁传过来的？
2. 检查输入数据："null 是从哪里来的？谁产生了这个值？"
3. 检查假设：你默认的某些条件是否不成立？
4. 隔离变量：注释掉一半代码看错误是否变化 → 二分法
5. 加诊断日志：`console.log()` / `print()` 关键路径的值

```
错误位置
  ↓
数据溯源（值/状态从哪里来）
  ↓
假设验证（这里真的是对的吗？）
  ↓
二分隔离（哪一半代码产生的问题）
  ↓
根因确认（"因为 A 为 null，所以 B 调用了 C.foo() 抛错"）
```

**工具：**
- Python: `pdb` / `breakpoint()` + 日志
- Node: `--inspect` + Chrome DevTools
- 数据流: 加 `print(type(x), repr(x))` 看类型和值

### 第三阶段：修复

**只改导致问题的那一点，不动其他。**

1. 最小化改动（禁止顺手重构附近的代码）
2. 改一处验证一处
3. 如果修复涉及条件逻辑，写个简表覆盖所有分支

```
根因确认
  ↓
修复方案（只改导致问题的那一点）
  ↓
验证（简化测试通过了吗？）
  ↓
回归（原来的功能还在吗？）
```

### 第四阶段：预防

**防止同一个 bug 再出现。**

1. 这个 bug 的类型是什么？（类型错误 / 边界条件 / 竞态条件 / 环境差异）
2. 同一类的 bug 还有没有其他可能潜伏的地方？
3. 是否应该加一个检查/断言/测试？

## 数据流向诊断法（典型问题）

```
用户输入 → 组件 A(state) → 组件 B(props) → 渲染输出
                              ↓
                         如果 B 不显示：
                         1. A 是否给了正确的 state？
                         2. B 收到的 props 是什么？
                         3. 条件渲染的哪个分支被执行了？
                         4. 样式是否被覆盖了？（检查 computed style）
```

## 常见陷阱

1. **跳步骤** — 看到现象直接猜原因改代码 → 90% 猜错，越改越乱
2. **修正主义** — 现象说"X 是 undefined"，你的修复是把 X 改成空对象 → 但根因是产生 X 的逻辑根本没执行
3. **忽略"它之前是能用的"** — 环境 / 依赖 / 配置变了什么？用 `git diff` 检查
4. **环境差异陷阱** — "开发环境能用"不代表代码没问题，可能开发环境装了不同版本

## 验证方法

1. ✅ 简化测试通过
2. ✅ 原始功能回归正常
3. ✅ 错误不再复现（至少 3 次）
4. ✅ 没有产生新的错误（检查控制台/日志）
